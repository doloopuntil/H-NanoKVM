# System 1.0.0 with application 3.0.0

The system moves from the vendor's Linux 5.10 to mainline Linux 6.18 LTS (6.18.29), with
the boot firmware, kernel and media drivers built from source. It includes everything in
[0.4.0](0.4.0.md), which was never published on its own. The
[migration plan](../development/kernel-6x-migration-plan.md) has the details and the
measurements behind each change.

## Getting it

There are no published release assets or update channels for 1.0.0 yet. Build the image
with the [CI image build](../development/ci-image-build.md) and flash it
([Install](../guide/install.md)). A device on a 5.10 system (0.3.x or 0.4.0) moves to 1.0.0
by flashing the SD card; there is no in-place update from 5.10.

## Hardware

- Supported: the NanoKVM Lite, the Full (Cube) and the PCIe version. Only the Lite has been
  tested on hardware; the Full and PCIe support was done by review.
- Dropped: the early-access Full ("alpha", OLED at I2C address `0x3d`).

## New

- Linux 6.18.29 with the licheerv patch series and our board patches, configured from our
  own lean config, with the Sophgo media drivers ported to it.
- Boot chain from source: the FSBL from the pinned SDK, OpenSBI 1.8.1 and U-Boot 2025.10.
  The kernel, device tree and recovery initramfs come in one FIT whose hashes U-Boot checks.
- A `reboot` is an RTC warm reset, so the boot reason reads `restart`; only a real hang
  reads `watchdog`.
- TCP tuning for the video: a 16 KiB unsent threshold (`tcp_notsent_lowat`), so MJPEG frames
  do not pile up in the socket, and no slow start after an idle pause. Ethernet receive batching
  is on (`gro_flush_timeout` 200 µs, `napi_defer_hard_irqs` 2): during an upload with the stream
  open, receive interrupts drop from about 2,900 to 300 a second, an uploaded MB costs about 14%
  less CPU and the two together move about 14% more data. It can be turned off
  ([Files on the device](../reference/device-files.md)).
- The web UI's scripts and style sheets are sent gzip-compressed (about a third of the size)
  and cached by the browser; the package carries the compressed copies, so the device does no
  compression.
- The boot watchdog checks the server over plain HTTP on loopback, also in HTTPS mode, instead
  of a TLS handshake every 10 seconds.
- Kernel: unused options left over from the architecture defaults are off (SysV IPC, POSIX
  message queues, the loop device, rpmsg, spare USB gadget functions), kernel
  addresses are hidden from `/proc/kallsyms`, and ICMP redirects are ignored.
- Connection limits: 256 open connections in total, 64 per source, 16 TLS handshakes at once,
  and 30 seconds to send request headers, so a silent or idle connection no longer holds its
  place; the logs kept in RAM are capped at 1 MiB.
- The Sophgo middleware, `libkvm` and `kvm_system` are built with the stack protector.
  `libkvm`, `libkvm_mmf` and `kvm_system` are also linked with full RELRO, `kvm_system` is
  position-independent (its address is randomised), and `libkvm` exports only its C API.
- `/tmp` and `/dev/shm` are mounted `noexec,nosuid,nodev`. The server and `kvm_system` run from
  `/kvmapp` instead of copies in `/tmp`, which also gives back the RAM those copies held (about
  8 MB of the 160 MB); the raw system updater stages its tools in `/run`.
- No STUN server by default: the device no longer contacts `stun.l.google.com` for a WebRTC
  session. Set `stun` in `server.yaml` for viewers behind another NAT.
- The kernel's random pool is seeded at boot from the SoC's hardware random number generator,
  read by U-Boot (a driver from NanoKVM-OS). Before, the pool was not ready until about 12
  seconds after boot.
- The web server encrypts with rustls only. Kernel TLS, tried during development, is not in
  this release ([why](../development/c906l-offload.md#kernel-tls-removed)).
- The server allocates memory with mimalloc instead of musl's allocator: MJPEG over HTTPS on a
  Lite went from 25.8 to 28.6 fps, about 12% less CPU per MB sent. It runs in mimalloc's
  secure mode (guard pages, encoded free lists), which costs under 1%.
- TLS records are encrypted and decrypted on the C906's vector unit (still ChaCha20-Poly1305;
  ring keeps the handshake). On a Lite at 1050 MHz, MJPEG over HTTPS uses 27% less CPU per MB
  and reaches the Wi-Fi link limit (36.7 to 43.1 fps). During an ISO upload the stream went
  from 11.8 to 15.2 fps and the upload from 5.8 to 7.1 MB/s.
- MJPEG frames are read and encoded at most two frames ahead of what viewers have taken. A
  stalled viewer (a sleeping laptop, a dropped connection) no longer keeps the encoder at full
  rate (the device sat at 56% CPU with nothing sent), and during an upload the encoder no longer
  makes frames that are then dropped.
- The MJPEG view stops its stream after the page has been hidden for 5 seconds and reconnects
  when it is shown again; browsers otherwise keep loading it in a background tab.
- Fewer copies per frame: an H.264 frame and its direct-stream packet share one buffer, and an
  MJPEG frame goes out in two pieces instead of three.
- `libkvm` copies each encoded frame once, from the encoder straight into the server's memory,
  instead of into a buffer of its own that the server copied again. MJPEG over HTTPS on a Lite
  went from 66.6 to 59.5 ms of CPU per MB sent (11% less), and the server's page faults from
  about 2,950 to 2 a second, as the per-frame buffer no longer comes from fresh pages.
- The raw capture frame (about 3 MB at 1080p) is mapped into the server, and invalidated in the
  CPU cache, only when the CPU reads it: for frame detection, or when rows must be repacked.
  Before, every frame was mapped and invalidated twice, about 0.8 ms per frame; MJPEG now uses
  3% less server CPU per MB.
- Keyboard and mouse input runs on a thread of its own, so it no longer waits behind the video
  and uploads on the server's one worker thread. With the stream open during an upload, input
  waits a few milliseconds instead of about 100.

## Hardening

- SSH keys are managed in **Settings > Network > Services > SSH keys**. Once a key is
  registered, or while two-factor sign-in is on, SSH accepts keys only, so the web password
  no longer opens a root shell on its own. Adding a key asks for the password and the code
  again.

- No `/dev/mem` or `/dev/port`, and no `devmem` in BusyBox: media buffers are mapped through
  `/dev/cvi-sys`, which accepts only buffers the carveout handed out, for mapping and for
  cache flushes and invalidates alike, and the RTC registers are read through nvmem.
- Signed kernel modules only, with a key each build generates and discards, and kernel
  lockdown in integrity mode.
- Memory-safety options: hardened usercopy, `FORTIFY_SOURCE`, slab freelist hardening and
  buckets, zeroing on free, list hardening, kernel stack offset randomisation and the
  stack-end check. They cost nothing measurable in MJPEG streaming; booting with zeroing on
  free turned off changed MJPEG CPU use by under 1%.
- KASLR: the kernel's virtual address is randomised at every boot, from a seed U-Boot reads
  from the hardware random number generator; the kernel clears the seed after reading it.
- The 5.10 kernel's hardening carries over (see [Security model](../reference/security-model.md)),
  and BSD ptys and `/proc/<pid>/pagemap` stay off as on 5.10.
- BusyBox is not setuid, and every account but root is locked, as on 0.4.0. The first
  6.x builds had missed both; the image build now checks them.
- HSTS (180 days) while a Tailscale or Let's Encrypt certificate is in use; browsers ignore it
  for the self-signed certificate and IP addresses, so it is not sent there
  ([HTTPS certificate](../guide/https-certificate.md#hsts)).

## Removed

- The 5.10 build: its workflow, Buildroot config, kernel and module scripts, and the
  vendor-SDK stock build.
- The firewall's iptables fallback: the system has only nftables.
- MaixCDK and OpenCV. `libkvm`, `libkvm_mmf` and `kvm_system` are plain CMake builds, and
  `libkvm` drives the capture channel and the JPEG encoder through `libkvm_mmf` directly.
  The four OpenCV libraries and `libgomp` (4.4 MB) leave `/kvmapp/server/dl_lib`, `libkvm.so`
  shrinks from 1.65 MB to 44 KB and `kvm_system` from 356 KB to 85 KB: `dl_lib` goes from
  8.8 to 2.8 MB, the root filesystem uses 6.2 MB less and the compressed SD image is 3 MB
  smaller (33.3 to 30.3 MB). An MJPEG frame is copied once less on its way out of `libkvm`.
- The second toolchain. Buildroot's GCC 14.4, which builds the rest of the system, now also
  builds the Sophgo middleware, `libkvm`, `libkvm_mmf` and `kvm_system`, with the same T-Head
  scalar extensions as musl and no vector code. The T-Head GCC 10.2 download and its
  `libstdc++`, `libgcc_s` and `libatomic` copies in `/kvmapp/server/dl_lib` are gone: the
  native code uses the libraries Buildroot installs in `/usr/lib`, and `libgomp` leaves the
  root filesystem. `dl_lib` goes from 2.8 to 1.1 MB, the root filesystem uses 1.9 MB less and
  the compressed SD image is 0.4 MB smaller (30.3 to 30.0 MB).
